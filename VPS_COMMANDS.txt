 STEP 1 — PRE-FLIGHT (already done; re-run only if the box changed)
───────────────────────────────────────────────────────────────────────────

Use grep -R (capital), never -r: sites-enabled is symlinks and lowercase -r
skips them silently. Do not put "!!" in a double-quoted echo — bash history
expansion mangles the line.

echo "=== is 8010 free? ==="; ss -tlnp | grep -E ':(8010)\b' || echo "8010 free"
echo "=== nginx map ==="; sudo nginx -T 2>/dev/null | grep -E "^# configuration file|server_name |listen " | sed 's/^[[:space:]]*//'
echo "=== locations ==="; sudo nginx -T 2>/dev/null | grep -E "^[[:space:]]*(location|proxy_pass|alias) " | sed 's/^[[:space:]]*//'

───────────────────────────────────────────────────────────────────────────
 STEP 3 — PORTFOLIO: SYSTEMD  (still invisible to visitors)
───────────────────────────────────────────────────────────────────────────

Generates the unit from your real user and paths. Do NOT install
deploy/hiimion.service directly — it assumes the laptop layout and its
ProtectHome would block SQLite writes under /root.

cd "$HOME/HiImIon"
APP="$HOME/HiImIon"; RUNAS="$(whoami)"
sudo tee /etc/systemd/system/hiimion.service > /dev/null <<EOF
[Unit]
Description=labustagialla.it portfolio (Django + Gunicorn)
After=network.target

[Service]
Type=simple
User=$RUNAS
WorkingDirectory=$APP
EnvironmentFile=$APP/.env
ExecStart=$APP/venv/bin/gunicorn hiimion.wsgi:application --bind 127.0.0.1:8010 --workers 3 --timeout 30 --access-logfile - --error-logfile -
ExecReload=/bin/kill -s HUP \$MAINPID
Restart=always
RestartSec=5

NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=full
ReadWritePaths=$APP
ProtectKernelTunables=true
RestrictSUIDSGID=true

[Install]
WantedBy=multi-user.target
EOF

sudo systemctl daemon-reload
sudo systemctl enable --now hiimion
sleep 2
systemctl status hiimion --no-pager | head -12

4b. MIGRATION CONFLICT — "multiple leaf nodes in the migration graph".

DO NOT run "makemigrations --merge" on the VPS. It writes yet another file
that exists only here, deepening the divergence, and the next git pull will
refuse to overwrite it.

DIAGNOSED STATE OF THIS BOX (2026-08-02), for reference:

  repo history is LINEAR:  0001 → 0002 → 0003_access_log → 0004_membership
                           (0003_access_log creates BOTH AccessLog and
                            ActivityLog)

  VPS has two extra UNTRACKED files, both applied:
      0003_activitylog.py
      0004_merge_0003_access_log_0003_activitylog.py

  applied: 0001, 0002, 0003_activitylog, 0003_access_log, the merge
  pending: 0004_membership   (depends on 0003_access_log, which IS applied)
  tables:  blog_category, blog_sitesettings, blog_article, blog_book,
           blog_accesslog, blog_activitylog     — no blog_membership yet

  django_migrations ids jump 19 → 21, so a row was deleted by hand once.
  That is how 0003_access_log got recorded as applied even though
  blog_activitylog already existed — it would otherwise have failed with
  "table already exists".

  Verdict: the server is ahead of git only in BOOKKEEPING. The tables on disk
  are exactly what the repo's linear history produces. So reconverge the
  server onto the repo instead of importing its artifacts into git forever.

Re-run the diagnostic if the box has changed since:

cd /root/writerblog && source venv/bin/activate
echo "=== migration files ==="; ls blog/migrations/
echo "=== tracked by git? ==="; git status --short blog/migrations/

4b-i. CONFIRMED (2026-08-02): the two VPS-only files were inspected.

  0003_activitylog.py creates ActivityLog with field-for-field IDENTICAL
  definitions to the ActivityLog block inside the repo's 0003_access_log
  (action varchar(10) + same choices, model_name varchar(30), object_title
  varchar(250), timestamp auto_now_add, user FK null=True SET_NULL, ordering
  ['-timestamp']).

  0004_merge_… has operations = [] — a pure graph join, no schema effect.

  So the table on disk is exactly what the repo's history produces.
  => FIX A applies. FIX B is not needed on this box.


4b-ii. FIX A — reconverge on the repo's linear history (no schema change)

Paste as ONE block. It is a && chain with two guards: it stops before
mutating anything if the STEP 0 backup is missing, or if blog_activitylog's
columns are not exactly what the model expects. Both guards were tested
against a deliberately mismatched database — nothing is touched when they fire.

cd /root/writerblog && source venv/bin/activate && \
ls /root/writerblog-db.bak-*.sqlite3 >/dev/null 2>&1 && echo "guard 1: backup ok" && \
python -c "
import sqlite3,sys
c=sqlite3.connect('db.sqlite3')
cols={r[1] for r in c.execute('PRAGMA table_info(blog_activitylog)')}
exp={'id','action','model_name','object_title','timestamp','user_id'}
print('columns:',sorted(cols))
sys.exit(0 if cols==exp else 1)" && echo "guard 2: schema ok" && \
mkdir -p /root/writerblog-vps-only-migrations && \
mv blog/migrations/0003_activitylog.py \
   blog/migrations/0004_merge_0003_access_log_0003_activitylog.py \
   /root/writerblog-vps-only-migrations/ && \
rm -rf blog/migrations/__pycache__ && \
python -c "
import sqlite3
c=sqlite3.connect('db.sqlite3');cur=c.cursor()
cur.execute(\"delete from django_migrations where app='blog' and name in ('0003_activitylog','0004_merge_0003_access_log_0003_activitylog')\")
print('deleted',cur.rowcount,'rows (expected 2)')
c.commit()" && \
python manage.py showmigrations blog

If "guard 1" does not print, run the STEP 0 backup first.
If "guard 2" does not print, STOP and use FIX B.

CHECK before migrating:
  [X] 0001_initial
  [X] 0002_book
  [X] 0003_access_log
  [ ] 0004_membership     ← the only unapplied one, and the only leaf
  No 0003_activitylog or 0004_merge_* lines at all.

If that is what you see, continue to 4c. If not, restore and stop:

What that file changes, all on the writerblog side:
  /static/       → /blog/static/
  /panel/login/  → /blog/panel/login/
  /django-admin/ → /blog/django-admin/
  location /     → location /blog/
  /media/        → DELETED, not renamed. gate_views.protected_media puts
                   uploads behind a membership check, so Django must serve
                   them; an nginx alias hands them to anyone with the URL.
  + X-Forwarded-Proto on every blog block — writerblog sets
    SECURE_PROXY_SSL_HEADER but nginx never sent the header, so Django saw
    every HTTPS request as plain HTTP.
/ezbk/, the festival include and all TLS directives are unchanged.

nginx broken, or you want the blog back at / :
    sudo cp /root/writerblog-nginx.bak-<timestamp> /etc/nginx/sites-available/writerblog
    sudo nginx -t && sudo systemctl reload nginx
    (that backup predates the swap, so it restores blog-at-root exactly)

Portfolio code bad:
    cd "$HOME/HiImIon" && git log --oneline -5
    git checkout <previous-sha> && sudo systemctl restart hiimion
    (its database holds only page views — rolling back is always safe)

Writerblog database damaged by a migration:
    systemctl stop writerblog
    cp /root/writerblog-db.bak-<timestamp>.sqlite3 /root/writerblog/db.sqlite3
    systemctl start writerblog

FIX A went wrong — put the migration graph back exactly as it was:
    systemctl stop writerblog
    cp /root/writerblog-db.bak-<timestamp>.sqlite3 /root/writerblog/db.sqlite3
    mv /root/writerblog-vps-only-migrations/*.py /root/writerblog/blog/migrations/
    rm -rf /root/writerblog/blog/migrations/__pycache__
    systemctl start writerblog
    (the db backup restores the two django_migrations rows, and the mv restores
     the files that back them — the two must go back together or the graph
     will not match)

Take the portfolio down entirely:
    sudo systemctl stop hiimion && sudo systemctl disable hiimion
    (then roll nginx back, or / will 502)
